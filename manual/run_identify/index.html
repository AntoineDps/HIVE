    run_identify¶

    Identifies model parameters or data-driven surrogates from CFD reference data using a pluggable scheme system.

    Usage¶

    python -m script.run_identify --case <name>.json

    Config files <name>.json live in inputs/identify_case/. The filename stem becomes the output folder name under source/models/.

    Rerun options¶

    When the output folder already exists, the script prompts:

    [1] erase and redo
[2] stop, do nothing
[3] load saved figures     — reopen existing .pkl plots interactively
[4] save with date suffix  — run and save under <name>_YYYYMMDD (keeps existing folder)

    Option [4] is useful to keep previous identification results while running a new one.

    What it does¶

    1. Loads the base model definition from source/models/<base_model>/model.json
    2. Creates a DDFeed — loads training data and runs scheme.prep()
    3. Creates an Optimizer — owns simulation helpers and delegates to scheme.run()
    4. Computes time margins (t_warmup, t_causal) from the base model and BEM data
    5. Saves identified parameters, result JSON, simulation CSVs and plots to source/models/<name>/identification/

    Input JSON config¶

    The config format differs between schemes because waves_train has a different structure. Two examples are provided below.

    Example — viscous_drag¶

    {
  "scheme": "viscous_drag",
  "base_model": "linear",
  "waves_train": ["example_cases"],
  "scheme_params": {
    "type": "force",
    "search": "opt",
    "c_v_min": 0,
    "c_v_max": 5000,
    "n_points": 50,
    "objective": "rmse_x"
  },
  "solver": {
    "method": "rk4",
    "dt": 0.05,
    "interpolation": {}
  }
}

    Example — pi_gain¶

    {
  "scheme": "pi_gain",
  "base_model": "linear",
  "waves_train": [
    {"type": "cfd_case", "case_name": "example_cases"},
    {"type": "synthetic", "T": 7.0, "H": 2.0, "duration": 120.0}
  ],
  "scheme_params": {
    "method": "grid",
    "B_min": 0,
    "B_max": 1000000,
    "K_min": -1000000,
    "K_max": 1000000,
    "n_B": 20,
    "n_K": 20,
    "objective": {"name": "mean_P_abs", "direction": "maximize"},
    "stability": {"enabled": true, "r": 5.0},
    "n_jobs": -1
  },
  "solver": {
    "method": "rk4",
    "dt": 0.05,
    "interpolation": {}
  }
}

    Top-level fields¶

    Field Type Description
    scheme string Identification scheme to use. See Available schemes
    base_model string Folder name under source/models/ for the base physics model (e.g. "linear"). Must contain model.json. Use "none" to disable physics simulation
    waves_train list Training data sources. Format depends on scheme — see per-scheme tables below
    scheme_params dict Scheme-specific parameters — see per-scheme tables below
    solver dict Solver settings used for forward simulations during identification

    solver fields¶

    Field Type Description
    method string Integration method: "euler" | "rk2" | "rk4" (case-insensitive)
    dt float Simulation timestep (s)
    interpolation dict Per-force-term interpolation flags: {"fe": bool, "fk": bool, "eta_hs": bool}

    Multiple waves_train entries — data pooling¶

    All entries in waves_train are loaded and merged into a single flat pool of wave cases. Identification runs on all of them together — there is no separate pass per entry.

    For viscous_drag, this means the global \(c_v\) is optimised over the concatenated signal from all cases at once, and each case also gets its own per-case \(c_v\). Adding more entries simply widens the training distribution.

    For pi_gain, gains are always per sea state — each loaded wave case gets its own optimal \((B_{pto}, K_{pto})\) regardless of how many waves_train entries there are.

    Multiple methods — method comparison¶

    Both schemes accept multiple methods simultaneously (a list for pi_gain; lists for type and/or search in viscous_drag). All combinations run in the same execution. result.json stores one block per method so results can be compared.

    For viscous_drag, model.json is automatically written using the method with the best global metric across all methods run. All other method results remain in result.json for manual inspection.

    // viscous_drag — run all four type × search combinations in one go
"type":   ["force", "response"],
"search": ["opt", "grid"]
// → runs: force_opt, force_grid, response_opt, response_grid

    // pi_gain — compare analytical, grid, and optimiser
"method": ["analytical", "opt", "grid"]

    Available schemes¶

    scheme What it identifies
    viscous_drag Quadratic drag coefficient \(c_v\)
    pi_gain Per-sea-state PI controller gains \(B_{pto}\), \(K_{pto}\)

    Note: linear_si is not yet implemented.

    Scheme: viscous_drag¶

    waves_train format¶

    A list of strings — each string is the stem of a handled data folder under data/handled/.

    "waves_train": ["example_cases", "other_cases"]

    scheme_params fields¶

    Field Type Default Description
    type string — Identification type: "force" (match \(f_{hyd}\)) or "response" (match \(x\), \(\dot{x}\))
    search string — Search method: "opt" (scalar optimiser) or "grid" (uniform sweep)
    base_force string "fhyd_lin" Reference force column used when type = "force"
    c_v_min float — Lower bound for \(c_v\) search [N·s²/m²]
    c_v_max float — Upper bound for \(c_v\) search [N·s²/m²]
    n_points int — Number of grid points (used when search = "grid")
    objective string or dict "rmse_x" Objective metric. See Objectives

    The four method combinations (type × search) are: force_opt, force_grid, response_opt, response_grid.

    Per-case vs global identification¶

    For every method, viscous_drag always produces two \(c_v\) values:

    • per-case — \(c_v\) fitted independently to each wave case (captures sea-state variability)
    • global — single \(c_v\) fitted across all cases pooled together (what goes into model.json)

    The global value is what is saved into model.json as the identified coefficient.

    Outputs — result.json¶

    {
  "scheme": "viscous_drag",
  "objective": {"name": "rmse_x", "direction": "minimize"},
  "results": {
    "force_opt": {
      "c_v_global": 1850.0,
      "metric_global": 0.09,
      "metric_label": "rmse_x",
      "c_v_per_case": {"case_label_1": 1700.0, "case_label_2": 1950.0},
      "metric_per_case": {"case_label_1": 0.07, "case_label_2": 0.11},
      "c_v_mean": 1825.0,
      "c_v_std": 125.0
    }
  }
}

    Scheme: pi_gain¶

    waves_train format¶

    A list of dicts. Each entry specifies a wave source:

    "waves_train": [
  {"type": "cfd_case", "case_name": "example_cases"},
  {"type": "synthetic", "T": 7.0, "H": 2.0, "duration": 120.0}
]

    cfd_case entry fields:

    Field Type Description
    type string "cfd_case"
    case_name string Stem of a handled folder under data/handled/

    synthetic entry fields:

    Field Type Default Description
    type string — "synthetic"
    T float 7.0 Wave period (s)
    H float 2.0 Wave height (m)
    duration float 120.0 Signal duration (s)
    d float 200.0 Water depth (m)

    Note: pi_gain uses SELF_LOADING = True — it does not call load_training_data and handles wave loading internally.

    scheme_params fields¶

    Field Type Default Description
    method string or list "opt" Method(s) to run: "analytical" | "opt" | "grid". Accepts a list to run several methods and compare
    B_min float 0.0 Lower bound for \(B_{pto}\) [N·s/m]
    B_max float 1e6 Upper bound for \(B_{pto}\) [N·s/m]
    K_min float -1e6 Lower bound for \(K_{pto}\) [N/m]
    K_max float 1e6 Upper bound for \(K_{pto}\) [N/m]
    n_B int 20 Grid points along \(B\) axis (used when method = "grid")
    n_K int 20 Grid points along \(K\) axis (used when method = "grid")
    B_init float midpoint of range Initial value for "opt"
    K_init float midpoint of range Initial value for "opt"
    objective string or dict {"name": "mean_P_abs", "direction": "maximize"} Objective metric. See Objectives
    stability dict {"enabled": false, "r": 5.0} Early-stop stability check: stops integration if \|x − η\| > r. r defaults to the buoy radius if available
    n_jobs int 1 Parallel workers for grid search (-1 = all CPU cores)

    method = "analytical" requires that handled cases carry wave parameters (Te). It uses BEM data to compute complex-conjugate control gains directly — no simulation loop needed for identification.

    Outputs — result.json¶

    {
  "scheme": "pi_gain",
  "base_model": "linear",
  "objective": {"name": "mean_P_abs", "direction": "maximize"},
  "stability": {"enabled": true, "r": 5.0},
  "n_cases": 12,
  "results": {
    "grid": {
      "B_per_case": {"case_label": 42000.0},
      "K_per_case": {"case_label": -15000.0},
      "metric_per_case": {"case_label": 1250.3},
      "metric_label": "mean P_abs [W]"
    }
  }
}

    Objectives¶

    The objective field accepts either a string shorthand or a dict with explicit direction.

    "objective": "rmse_x"

"objective": {"name": "mean_P_abs", "direction": "maximize"}
    Name Description Default direction
    "rmse_x" RMSE of displacement \(x\) minimize
    "rmse_xdot" RMSE of velocity \(\dot{x}\) minimize
    "nrmse_x" Normalised RMSE of \(x\) minimize
    "nrmse_xdot" Normalised RMSE of \(\dot{x}\) minimize
    "mean_P_abs" Mean absorbed power \(P_{abs}\) maximize
    "rmse_P_abs" RMSE of absorbed power minimize

    Available base models¶

    The base_model field is a folder name under source/models/. The folder must contain a model.json. BEM data (HydroSphere pickle) is loaded from source/models/bem/ as referenced inside model.json.

    Folder Description
    linear Linear potential-flow model with state-space radiation

    Outputs¶

    source/models/<name>/
├── <name>.json               ← copy of the config used
├── model.json                ← model definition updated with identified parameters
├── run.log
└── identification/
    ├── result.json           ← identified parameters and objective value per method
    ├── data/
    │   └── *.csv             ← simulated time series at best parameter values
    └── plots/
        ├── *.png
        └── *.pkl             ← interactive figure snapshots

    Notes¶

    • The base model must exist at source/models/<base_model>/model.json before running run_identify.
    • t_warmup and t_causal are computed automatically from the base model IRF lengths and applied as simulation clip margins to all simulated trajectories.
    • For viscous_drag, multiple waves_train entries are pooled into one training set. The global \(c_v\) (fit across all pooled cases) is written to model.json; per-case values are in result.json for inspection.
    • For pi_gain, gains are identified per sea state — there is no global coefficient. Multiple waves_train entries simply extend the set of sea states covered.
    • Running several methods at once produces one result block per method in result.json. For viscous_drag, model.json is automatically written from the best-performing method (lowest global metric). For pi_gain there is no automatic model.json — all results are in result.json.
