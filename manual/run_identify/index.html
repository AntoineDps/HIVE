    run_identify¶

    Identifies model parameters or data-driven surrogates from CFD reference data using a pluggable scheme system.

    Run¶

    first run¶

    python -m script.run_identify --case <name>.json

    Config files <name>.json live in inputs/identify_case/. The filename stem becomes the output folder name under source/models/.

    rerun options¶

    When the output folder already exists, the script prompts:

    [1] erase and redo
[2] stop, do nothing
[3] load saved figures     — reopen existing .pkl plots interactively
[4] save with date suffix  — run and save under <name>_YYYYMMDD (keeps existing folder)

    Option [4] is useful to keep previous identification results while running a new one with same JSON input.

    available schemes¶

    Scheme Description Note
    "viscous_drag" identify a viscous drag coefficient given a base model to fit CFD reference data see Scheme: viscous_drag
    "pi_gain" find optimal PI gain (stiffness and damping coefficient) to maximize or minimize an objective, absorbed power for instance see Scheme: pi_gain

    what it does¶

    Run an optimization depending on the chosen identification scheme and based on a chosen model. More explicitely:

    1. Loads the base model definition from source/models/<base_model>/model.json
    2. Creates a DDFeed — loads training data and runs scheme.prep()
    3. Creates an Optimizer — owns simulation helpers and delegates to scheme.run()
    4. Computes time margins (t_warmup, t_causal) from the base model and BEM data
    5. Saves identified parameters, result JSON, simulation CSVs and plots to source/models/<name>/identification/

    Scheme: viscous_drag¶

    Identifies the quadratic drag coefficient \(c_v\) in \(f_{visc} = -c_v |\dot{x}| \dot{x}\) for:

    • per-case — \(c_v\) fitted independently to each wave case
    • global — single \(c_v\) fitted across all cases pooled together → corresponds to the model output written to model.json

    input JSON config¶

    {
  "scheme": "viscous_drag",
  "waves_train": [
    "example_cases"
  ],
  "base_model": "linear_sphere_r5",
  "scheme_params": {
    "base_force": "fe_lin",
    "type": ["force", "response"],
    "search": ["opt", "grid"],
    "c_v_min": 0,
    "c_v_max": 150000,
    "n_points": 10,
    "objective": "rmse_x"
  },
  "solver": {
    "method": "RK4",
    "dt": 0.05,
    "interpolation": {
      "fe": true,
      "eta_hs": true
    }
  }
}

    top-level entries¶

    Field Type Options / values Multiple entry (list) Description
    waves_train string Handled data folder name under data/handled/ Yes. All entries are loaded and merged into a single flat pool of wave cases Identification data
    base_model string model folder name under source/models/.See Model No Physics-bases model to augment with viscous drag.
    scheme_params dict see scheme_params table below No Scheme-specific parameters
    solver dict see Solver No Simulation solver settings

    scheme_params¶

    Field Type Default Options / values Multiple entry (list) Description
    type string — "force", "response" Yes Identification type. "force" fits \(c_v\) to match \(F_{hyd}\) ; "response" fits \(c_v\) to match \(x\), \(\dot{x}\)
    search string — "opt", "grid" Yes Search method. "opt" uses a bounded scalar optimiser ; "grid" sweeps a uniform grid over \([c_{v,min},\ c_{v,max}]\)
    base_force string "fhyd_lin" any column present in the DataHandle dataset No Force column (\(f_{col}\)) subtracted to reference force \(f_{hyd}\) type = "force", such as \(f_{hyd} = f_{col} + f_{visc}\)
    c_v_min float 0.0 any non-negative float [N·s²/m²] No Lower bound of the \(c_v\) search range
    c_v_max float 5000.0 any positive float [N·s²/m²] No Upper bound of the \(c_v\) search range
    n_points int 100 any positive integer No Grid resolution — used only when search = "grid"
    objective string "rmse_x" Any available metric. see Metric No Metric used to score \(c_v\) candidates

    The four possible type × search method combinations are: force_opt, force_grid, response_opt, response_grid. Pass lists to run several at once.

    Output¶

    The output structure is described below.

    source/models/<name>/
├── <name>.json               ← copy of the config used
├── model.json                ← model definition updated with identified parameters
├── run.log
└── identification/
    ├── result.json           ← identified parameters and objective value per method
    ├── data/
    │   └── *.csv             ← simulated time series at best parameter values
    └── plots/
        ├── *.png
        └── *.pkl             ← interactive figure snapshots

    Scheme: pi_gain¶

    Identifies per-sea-state PI controller gains \((B_{pto},\ K_{pto})\) that maximise an objective (default: mean absorbed power).

    input JSON config¶

    {
  "scheme": "pi_gain",
  "base_model": "linear_sphere_r5",
  "waves_train": [
    {"type": "cfd_case", "case_name": "example_cases"},
    {"type": "synthetic", "type_wave": "irr", "T": 7.0, "H": 2.0, "duration": 120.0, "gamma": 3.3}
  ],
  "scheme_params": {
    "method": ["analytical", "grid", "opt"],
    "B_min": 0,
    "B_max": 500000,
    "K_min": -200000,
    "K_max": 0,
    "n_B": 5,
    "n_K": 5,
    "B_init": 200000,
    "K_init": -100000,
    "objective": {"name": "mean_P_abs", "direction": "maximize"},
    "stability": {"enabled": true, "r": 5.0},
    "n_jobs": -1
  },
  "solver": {
    "method": "rk4",
    "dt": 0.05,
    "interpolation": {"fe": true, "eta_hs": true}
  }
}

    top-level entries¶

    Identification runs on all of them together — there is no separate pass per entry.

    Field Type Options / values Multiple entry (list) Description
    waves_train dict See waves_train Yes. All entries are loaded and merged into a single flat pool of wave cases Sea states profile, synthetic or CFD based, on which is based the PTO gain identification
    base_model string model folder name under source/models/. See Model No Model on which is based the PTO gain identification
    scheme_params dict see scheme_params below No Scheme-specific parameters
    solver dict see Solver No Simulation solver settings

    waves_train fields¶

    Field Type Default Options / values Description
    type string — "synthetic" for wave generated by addition of regular wave components. "cfd_case" for wave elevation from CFD based data Wave elevation source
    case_name string — handled data folder case name under data/handled/ handled data folder case name. Only when type = "cfd_case"
    wave_type string "reg" "reg" (regular sinusoid) · "irr" (irregular JONSWAP) Wave type. Only when type = "synthetic"
    T float — any positive float (s) Wave period (regular) or energy period (irregular). Only when type = "synthetic"
    H float — any positive float (m) Wave height (regular) or significant wave height (irregular). Only when type = "synthetic"
    gamma float None any positive float JONSWAP peak enhancement factorwave_type = "irr". Only Only when type = "synthetic" and wave_type = "irr"
    duration float 100.0 any positive float (s) Signal duration. Only when type = "synthetic"

    scheme_params fields¶

    Field Type Default Options / values Multiple entry (list) Description
    method string "opt" "analytical" (from linear potential flow theory, does not consider bounds values)· "opt" using an optimizer· "grid" doing a grid-search· or a list of several Yes Identification method(s). Pass a list to run and compare multiple methods in one execution
    B_min float 0.0 any float [N·s/m] No Lower bound for \(B_{pto}\) search
    B_max float 1e6 any float [N·s/m] No Upper bound for \(B_{pto}\) search
    K_min float -1e6 any float [N/m] No Lower bound for \(K_{pto}\) search
    K_max float 1e6 any float [N/m] No Upper bound for \(K_{pto}\) search
    n_B int 20 any positive integer No Grid points along \(B\) axis — used only when method = "grid"
    n_K int 20 any positive integer No Grid points along \(K\) axis — used only when method = "grid"
    B_init float midpoint of [B_min, B_max] any float [N·s/m] No Initial value for the "opt" optimiser
    K_init float midpoint of [K_min, K_max] any float [N/m] No Initial value for the "opt" optimiser
    objective dict {"name": "mean_P_abs", "direction": "maximize"} see Metric for ´"name´, "maximize" or "minimize" for ´"direction"´ No Metric used to score \((B, K)\) candidates
    stability dict {"enabled": false, "r": 5.0} enabled: true / false · r: float (m) No Early-stop check: aborts integration if \(\|x - \eta\| > r\). r defaults to buoy radius if not set
    n_jobs int 1 any integer · -1 = all CPU cores No Parallel workers for "grid" search via joblib

    The "analytical" method is based on linear potential flow theory and hence limited to regular waves. While it does not hold for irregular waves, the energy period is still used.
