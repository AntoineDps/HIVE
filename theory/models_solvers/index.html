    Models & Solvers¶

    Model types¶

    A model in HIVE is a folder under models/ containing a model.json file. The JSON records the model's physics components, identified parameters, and metadata. Currently supported model types:

    Model key Description
    linear Cummins equation with radiation state-space, linear PTO
    linear_viscous As linear, plus quadratic drag $c_v

    Models identified by run_identify inherit a base model's model.json and add or update the identified parameters.

    model.json structure¶

    {
  "type": "linear_viscous",
  "hydro_sphere_pkl": "r5",
  "radiation": {
    "A": [[...], ...],
    "B": [[...]],
    "C": [[...]],
    "D": [[...]]
  },
  "hydrostatic": {
    "K_hs": 142000.0
  },
  "added_mass_inf": 450.0,
  "mass": 1200.0,
  "c_v": 1850.0,
  "t_warmup": 15.0,
  "t_causal": 3.2
}

    The radiation block holds the state-space matrices \((A_{rad}, B_{rad}, C_{rad}, D_{rad})\) fitted from the BEM IRF. These are written by run_handle_data during the first call that initialises the BEM data.

    SimRun¶

    SimRun is the class responsible for running a single forward simulation. It:

    1. Loads the model definition from model.json
    2. Instantiates the radiation state integrator
    3. Steps the ODE forward using the chosen solver
    4. Returns a dataset attribute (a pandas.DataFrame) with the same column schema as DataHandle

    Because SimRun and DataHandle expose the same .dataset and .label interface, they can be mixed in plotter calls.

    ODE solvers¶

    The solver block in validate and identify configs selects the numerical integrator:

    "solver": {
  "method": "RK4",
  "dt": 0.05,
  "interpolation": {}
}
    Method Description
    RK4 4th-order Runge–Kutta (recommended)
    RK2 2nd-order Runge–Kutta (Heun's method)
    euler Forward Euler (1st order, fast but inaccurate)

    The integration timestep dt is independent of the CFD data's native timestep. HIVE interpolates the forcing signals (wave elevation, excitation force) onto the solver grid using the scheme specified in interpolation.

    Warmup period¶

    The radiation state-space system starts at rest (\(\mathbf{z}_{rad} = 0\)). It takes several wave periods for the radiation states to converge to their quasi-steady values. HIVE computes t_warmup automatically from the pole magnitudes of \(A_{rad}\):

    \[ t_{warmup} = \frac{-\log(\epsilon)}{\min_k |\text{Re}(p_k)|} \]

    where \(\epsilon\) is a small tolerance (default \(10^{-3}\)) and \(p_k\) are the eigenvalues of \(A_{rad}\). The value is logged in run.log and saved in result.json.

    Metrics are computed only over \([t_{warmup},\; T_{end} - t_{causal}]\).

    Forcing signal interpolation¶

    Why interpolation is needed¶

    The excitation force \(f_e^{lin}\) and wave elevation \(\eta\) are precomputed on a fixed grid — the timestep of the handled CFD data (set by dt in the handle config). The ODE solver may use a different timestep. At each stage of the integrator (e.g. the four stages of RK4), the forcing signals must be evaluated at intermediate time points that generally do not fall on the original grid, requiring interpolation.

    Note that \(f_e^{lin}\) is state-independent — it does not depend on \(x\) or \(\dot{x}\) — so it is fully precomputed before integration begins. This is unlike the radiation force \(f_{rad}\), which is stepped forward as a state-space system at each stage, or \(f_{hs}\) and \(f_{pto}\), which are evaluated from the current state.

    Interpolation schemes¶

    The interpolation dict in the solver config is passed directly to scipy.interpolate.interp1d via the kind keyword:

    kind Description Accuracy
    "linear" (default) Piecewise linear between grid points 2nd order in grid spacing
    "nearest" Zero-order hold — value at nearest grid point 1st order (step function)
    "quadratic" Piecewise quadratic spline 3rd order
    "cubic" Piecewise cubic spline 4th order

    Consistency with the ODE solver¶

    A subtle point: if you use RK4 ("method": "RK4") but hold the forcing constant within a step ("kind": "nearest"), the integration is effectively first-order in the forcing term. The radiation and restoring forces benefit from the full RK4 accuracy, but the excitation forcing does not. For best results, match the interpolation order to the solver:

    • RK4 / RK2: use "linear" or "cubic"
    • Euler: "nearest" (ZOH) is sufficient and cheapest

    In practice, "linear" is a good default — it is cheap and ensures that \(f_e^{lin}\) varies smoothly across RK stages.

    Practical note on grid resolution¶

    The interpolation error decreases as the handled data timestep decreases. If you notice artefacts in simulated time series (especially at high frequencies), try reducing dt in the handle config to produce a finer forcing grid, rather than switching to a higher-order interpolation scheme.
